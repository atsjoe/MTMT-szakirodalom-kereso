# MTMT Literature Search & Network Analysis Engine - Developer Documentation
**Version:** 2.3 (Robust Journal & Relevancy Engine + Elevated Search Bar Edition)  
**Architecture:** Client-Side Single Page Application (SPA), Vanilla HTML5/CSS3/JavaScript (ES6+)  
**Primary Data Sources:** MTMT v2 REST API (`https://m2.mtmt.hu/api/`), OpenAlex REST API (`https://api.openalex.org/`)  

---

## 1. System Architecture & Project Organization

The system operates strictly within the user's web browser environment (Serverless / Static SPA), with zero backend server or relational database dependencies. All state resides in memory, in `localStorage` (custom thesaurus), and within the live Document Object Model (DOM).

### 1.1. Technologies & Design Patterns
*   **Runtime Environment:** Client-side Web Platform. No local proxy or web server required.
*   **Language & Core APIs:** Vanilla ECMAScript 2020+ using asynchronous `fetch`, `Promise.all` concurrency, regular expressions, and the Blob/File API for local exports.
*   **UI/UX Architecture:** Dual-column responsive layout via CSS Grid. Dynamic dialog modals with backdrop filters. Active pre-filters seamlessly project into the main search bar as interactive chips (tokens) with explicit Boolean `AND` badges.
*   **Upstream REST APIs:**
    *   *MTMT v2 API:* Endpoint queries for publications, authors, serials/journals, and institutional hierarchies utilizing structured condition predicates (`cond`).
    *   *OpenAlex API:* Entity retrieval for works via canonical DOIs, OpenAlex identifiers (`W...`), and graph traversal using the `cites` co-citation operator.

### 1.2. File Manifest
* `index.html`: Main application entry point containing UI components, query builders, and formatting algorithms.
* `style.css`: Unified stylesheet controlling layout, search bar token badges, modal dialogues, and responsive breakpoints.
* `szotar.html`: Standalone local micro-service managing researcher thesauri in browser `localStorage`.
* `sugo.html`: User handbook and search query syntax manual.
* `mapping_mtmt_api.json`: Schema crosswalk documenting MTMT v2 publication objects.
* `mapping_openalex_api.json`: Schema crosswalk documenting OpenAlex Works objects.
* `mapping_export_formats.json`: Mapping dictionary for RIS, BibTeX, and CSL-JSON specifications.

## 2. Search Engines & Query Execution

### 2.1. Smart Query Parser (`okosKeresoFeldolgozo`)
* **Parsing Mechanism:** Regex tokenizer (`/(-?"[^"]+")|(-?[^\s]+)/g`).
* **Behavior:** Differentiates required include tokens from negated exclude tokens. Space boundaries signify implicit conjunction (`AND`), while quoted phrases enforce exact token matching (`"exact phrase"`).

### 2.2. Systematic Literature Review (SLR) Engine (`generaljKombinaciokat`)
* **Underlying Problem:** The MTMT API `cond` parameter is strictly linear and does not support nested Boolean syntax trees (e.g., arbitrary parenthesized combinations of `AND` and `OR`).
* **Algorithmic Solution:** The client-side engine computes the Cartesian product of all synonym rows. If Row A contains 3 terms (OR) and Row B contains 2 terms (OR), the system dispatches 6 individual, atomic queries in parallel (`Promise.all`). Incoming publication streams are unified into an in-memory `Set` indexed by `mtid` (MTMT identifier), eliminating duplicate records before rendering.

## 3. MTMT API Integration Solutions (Workarounds & Hardening)

Public legacy academic APIs frequently exhibit edge-case failures when exposed to complex multi-word strings. The following defensive architectures safeguard continuous user experience:

### 3.1. Dual-Query Strategy & Client-Side Verification for Serials
When searching journal titles (`journal` and `series`) in modal selectors:
1. **Tokenized Sub-Queries:** The user's input string is split by whitespace and submitted as individual `cond=label;any` parameters. This maintains server stability.
2. **Synchronous Exact Match:** Simultaneously, a secondary query executes using `cond=title;eq` to ensure high-priority target journals (e.g., exact matches like *"Magyar Tudomány"*) are not dropped due to page truncation.
3. **Strict Client-Side Conjunction Filter:** All records returning from the API pass through an in-memory predicate verifying that *every* input keyword appears in the title, filtering out false positives generated by fuzzy partial matches.

### 3.2. "Bulldozer" Pagination Engine (`fetchAllPages`)
* **Underlying Problem:** For certain complex filter criteria, the upstream MTMT server ignores the requested `size=2000` parameter and falls back to its default page size of 20 items.
* **Algorithmic Solution:** Upon parsing page 1, `fetchAllPages` inspects the `paging.totalPages` response attribute. If `totalPages > 1`, the engine dynamically schedules parallel asynchronous requests for all remaining pages (bounded up to 50 pages / 1000 items), aggregating the complete payload before display.

### 3.3. Cache-Buster Mechanism
* **Underlying Problem:** Aggressive browser caching can reuse stale, truncated HTTP responses for identical URLs.
* **Solution:** Modal searches append an epoch timestamp parameter: `&_t=${Date.now()}`, enforcing an end-to-end network trip for every user lookup.

### 3.4. Relevance Scoring Engine (`calcScore`) & Anti-Freeze Throttling
Incoming candidate entities in lookup modals are scored to place the best match at the top:
* **ISSN Regex Sanitization:** MTMT journal labels append ISSN numbers (e.g., *"Magyar Tudomány 0025-0325 1588-1245"*). The scoring engine strips these strings via regex (`/\s?[0-9]{4}-[0-9]{3}[0-9xX]/g`) prior to string comparison.
* **Scoring Heuristics:**
  - 100 points: Perfect exact string match.
  - 80 points: String starts with search term.
  - 60 points: Full phrase occurs contiguously.
  - 10 points: All terms present in scattered order.
  - Tie-breaking: Hungarian collation via `localeCompare('hu')`.
* **DOM Anti-Freeze Protection:** If a broad query yields over 1,000 matches (e.g., *"sustainable"*), the entire list is sorted in memory, but only the top 500 items are rendered into the DOM to avoid interface stutter.

## 4. Dynamic Pre-Filters & Tokenized Search Bar

### 4.1. Pre-Filters & Search Bar Synchronization
Pre-filters in the sidebar (Author, Journal, Institution, Publication Year, and Publication Role) attach as URL parameters prior to dispatch (`cond=authorships.author;eq;...`, `publishedYear;ge;...`, etc.). Simultaneously, they render into the elevated search bar as distinct interactive chips. Users can remove any filter directly via its chip `✕` button.

### 4.2. In-Memory Post-Filters (`kliensSzures`)
Once downloaded (up to 2,000 records), secondary filtering runs instantaneously in client memory:
* **Boundary-Aware Word Matcher (`pontosKereses`):** Uses regex boundaries (`(^|[^a-záéíóöőúüűA-ZÁÉÍÓÖŐÚÜŰ0-9])`) to differentiate whole words from substrings, while supporting wildcard asterisks (`*`).
* **Publication Role Derivation (`getPubAllapot`):** Resolves core source vs. citing status directly from Boolean attributes (`pub.core` and `pub.citation`).

## 5. Persistence, Thesaurus & Alerting

* **Session Export:** Serializes the entire GUI state (search terms, filter selections, active tokens, SLR matrices) into structured JSON and triggers a local Blob download.
* **Alerting & Novelty Detection:** Upon loading a saved session JSON, the user can activate the novelty filter. The engine compares publication `created` timestamps against the JSON's recorded export date (including a 24-hour safety buffer), isolating only newly indexed publications.
* **Researcher Thesaurus:** Micro-app (`szotar.html`) interacts directly with `localStorage` (key: `mtmtSajatSzotar`) with pure text file import/export.

---

## 6. Citation Export Engine & Reference Fixes

* **HTML Formatter:** Generates copy-pasteable references formatted according to **APA (7th)**, **IEEE**, **MLA (9th)**, and **Chicago (17th)** rules.
* **BibTeX Exporter:** Injects double curly braces `{{...}}` around title fields to enforce LaTeX case preservation.
* **RIS / BibTeX `internalId` Injection:** Many online-first or historical records in national databases lack standard page ranges (`SP`/`EP`). To prevent reference managers (such as Zotero, Mendeley, and EndNote) from rejecting records, the engine dynamically injects the MTMT database `internalId` into RIS `SP`/`M1` and BibTeX `artno` fields.

## 7. Bibliometric Network Discovery (OpenAlex Integration)

Added to unlock scientific exploration beyond traditional keyword retrieval by traversing OpenAlex's global knowledge graph:

### 7.1. Cross-System Entity Resolution
* Identifiers are extracted from the MTMT `identifiers` array by resolving `source.label === "DOI"` or `source.label === "OpenAlex"`.

### 7.2. Algorithmic Workflows
* **Bibliographic Coupling (Related Works):** Aggregates outgoing reference lists (`related_works`) across selected MTMT publications, deduplicates identifiers, and retrieves top 50 related items in a single query (`filter=openalex:W1|W2|...`).
* **Co-Citation Discovery & Bulk Rate-Limit Protection:** Identifies external works frequently cited alongside the target papers in third-party bibliographies. Rather than issuing parallel requests that trigger HTTP 429 errors, the system submits a consolidated query (`filter=cites:W1|W2|...`), aggregates citation co-occurrences, and presents the top 10 co-cited nodes.

### 7.3. Network Drawer & Data Normalization
* Candidate items populate an isolated visual drawer ("Hálózati Tálca") at the bottom of the interface.
* Clicking **`+ Hozzáadás`** normalizes the OpenAlex Work schema into MTMT's publication object structure (generating synthetic negative identifiers `oaFakeIdCounter` and flagging `isOpenAlex: true`), allowing seamless downstream export through the CSL-JSON, RIS, BibTeX, and HTML formatters.
